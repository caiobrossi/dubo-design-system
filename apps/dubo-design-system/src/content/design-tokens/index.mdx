<DocsSection
  id="architecture"
  title="3-layer token architecture"
  description="Dubo's design tokens follow a strict 3-layer hierarchy that separates raw values from intent and keeps component decisions local."
>
  <Callout tone="brand" title="OKLCH color format">
    All color primitives are defined in OKLCH — a perceptually uniform color space
    that produces consistent lightness across hues. This means a brand-500 and a
    success-500 look equally vibrant, making the palette composable by default.
  </Callout>

**Layer 1 — Primitives** are raw, context-free values: color scales (brand blue, slate,
indigo, cyan, teal, lime, yellow, orange, pink, tomato, error, warning, success, purple), radius steps, shadow depths, and spacing units.
They never appear directly in components.

**Layer 2 — Semantic** tokens map primitives to intent: `color-brand`, `color-bg-page`,
`color-text-primary`, `color-border`. They adapt to light/dark mode via CSS custom
properties and are what components should reference.

**Layer 3 — Component** tokens now exist only when a component keeps a truly unique
decision: examples include `btn-primary-shadow`, `segment-pill-shadow` or
`avatar-group-overlap`. Most sizing, spacing, color and typography concerns were
intentionally pushed back into shared semantic roles.

This composability means you can re-theme the entire system by swapping primitives,
adjust semantic intent for a product vertical, or override a single component —
without side effects.

</DocsSection>
